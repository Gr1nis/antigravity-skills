# Режим ПРО: Профессиональный инженерный workflow с ИИ (`vibe-pro`)

Этот скилл переводит агента из режима обычного ассистента в режим строгого инженерного пайплайна разработки ПО.
Обычные вопросы и быстрые консультации выполняются стандартно и легко без этого скилла.
При фразе-триггере: **«режим про»**, **«по пайплайну»** или **«pro mode»** агент обязан строго следовать данному регламенту.

---

## 1. Фундаментальный принцип: Защита от «подгонки под тесты» (Anti-Goodhart TDD)

Главная опасность ИИ при TDD — написание кода, который проходит только конкретные наивные ассерты, но ломается в продакшене.
Чтобы этого не происходило, скилл вводит строгие правила тестирования:

1. **Разделение ролей (Dual Mindset):**
   * **Этап тестов (Adversarial QA)**: Агент думает как беспощадный тестировщик, чья цель — *сломать* будущую реализацию.
   * Тесты должны покрывать:
     * Граничные значения (boundary values): 0, отрицательные числа, пустые строки/слайсы, максимальные лимиты.
     * Невалидный ввод и обработку ошибок (error returns, HTTP 4xx/5xx, невалидный JSON, SQL injection символы).
     * Конкурентность и гонки (data races, параллельные вызовы).
     * Идемпотентность и повторные вызовы.
2. **Инварианты и Property-Based тестирование:**
   * Помимо 2–3 фиксированных примеров, формулируются свойства системы (инварианты):
     * *Пример Go*: Баланс счета после 1000 конкурентных транзакций равен начальному плюс сумма изменений (`sync.WaitGroup`, каналы, `go test -race`).
     * *Пример C#/Unity*: Здоровье сущности никогда не превышает `maxHp` и не падает ниже 0 при любых последовательностях урона и хила.
     * Обратимость операций: `decode(encode(obj)) == obj`.
3. **Строгая фаза RED:**
   * Тесты запускаются ДО появления кода.
   * Тесты обязаны упасть **именно по причине нереализованной логики** (Assertion failure / NotImplemented), а не из-за синтаксической ошибки файла тестов.
4. **Анти-хардкод аудит:**
   * Запрещено писать в реализации `if x == 42 return "ok"` только чтобы закрыть конкретный тест. Код обязан реализовывать общий алгоритм и бизнес-логику.

---

## 2. Пошаговый регламент 5 фаз («Режим ПРО»)

```
[Фаза 1: Бриф & Опрос] ──> [Фаза 2: Спецификация & Репозиторий] ──> [Фаза 3: Adversarial TDD (Red)] ──> [Фаза 4: Реализация (Green)] ──> [Фаза 5: Рефакторинг & Sync]
```

---

### Фаза 1: Поступательный бриф (Интервью)

Вместо того чтобы сразу писать код, агент обязан остановить генерацию и провести интервью:
* **Первый раунд**: Задать **3–5 самых критических архитектурных вопросов** (формат данных, стек, требования к надежности, масштабированию или интеграциям).
* **Поступательность**: Если в процессе работы возникают неоднозначности, развилки логики или сильные сомнения — агент обязан остановиться и дозадать конкретный точечный вопрос, а не гадать.
* Вопросы формулируются четко, по возможности с вариантами ответа или рекомендацией (`(Рекомендуется)`).
* **Синергия с `prompt-master` («Улучшатель промптов»):** Если пользователь вызывает `vibe-pro` вместе с `prompt-master`, вопросы не дублируются — проводится единый опрос по 9 измерениям `prompt-master` + архитектурному брифу `vibe-pro`, после чего `prompt-master` формирует жесткий контракт задачи (Task Contract с `Done When` и инвариантами), который сразу передается в Фазу 2 без ручного копирования.

---

### Фаза 2: Спецификация и подготовка репозитория

1. **Создание артефакта реализации (`implementation_plan.md`)**:
   * Архитектура (пакеты, структуры, интерфейсы, API контракты).
   * Граничные условия и инварианты, которые будут защищены тестами.
   * Список изменяемых/создаваемых файлов.
2. **Синхронизация с GitHub (`Gr1nis`)**:
   * Для новых проектов или по запросу пользователя инициализируется локальный git-репозиторий.
   * Генерируется строгий и полный `.gitignore` под стек проекта:
     * Для Go: бинарники, `.env`, вендоры, профили покрытия.
     * Для Unity/C#: `[Ll]ibrary/`, `[Tt]emp/`, `[Oo]bj/`, `[Bb]uild/`, `*.csproj`, `*.sln`, `.vs/`.
     * Общие: секреты, токены, ОС-специфичные файлы (`Thumbs.db`, `.DS_Store`).
   * Если проект крупный — используется ветвление (`git checkout -b feature/...`) или изолированный `git worktree` для безопасных экспериментов.
   * При наличии авторизации (GitHub CLI / Personal Access Token) проект пушится в **приватный** репозиторий на аккаунт `Gr1nis`. Если токен еще не настроен — агент дает готовую инструкцию из 1 команды.

---

### Фаза 3: Adversarial TDD (Красная фаза)

1. Создается тест-сьют:
   * **Go**: Табличные тесты (`table-driven tests`), проверка конкурентности с `go test -v -race ./...`, бенчмарки при критичности производительности.
   * **C# / Unity / .NET**: Unit-тесты (`dotnet test`, xUnit/NUnit, Unity Test Framework).
2. Запуск тестов:
   * Команда запускается через терминал.
   * Фиксируется падение тестов (Red Phase). Тесты падают из-за отсутствия реализации.

---

### Фаза 4: Реализация (Зеленая фаза)

1. Разработка минимально достаточного, чистого и идиоматичного кода под спроектированные интерфейсы:
   * **Go**: Следование Clean Architecture, явная обработка ошибок (`errors are values`, `%w`), передача `context.Context` первым аргументом, отсутствие паник в бизнес-логике.
   * **C# / Unity**: SOLID, компонентный подход, отсутствие утечек памяти в событиях (`event -= Handler`), разделение данных (`ScriptableObject`) и логики.
2. Запуск тестов:
   * Тесты прогоняются повторно.
   * Если тест упал — агент анализирует трейсбек, исправляет причину и повторяет прогон до 100% зелёного статуса.

---

### Фаза 5: Рефакторинг, аудит инвариантов и Push

1. **Анти-чит аудит**:
   * Быстрая самопроверка: нет ли костылей, ложных упрощений или захардкоженных условий под конкретные ассерты.
2. **Кодовый стиль и линтинг**:
   * Для Go: `go vet ./...` (и `golangci-lint` при наличии).
   * Для C#: проверка предупреждений компилятора (`dotnet build`).
3. **Commit & Push**:
   * Создается понятный коммит по конвенции Conventional Commits (`feat: ...`, `test: ...`, `fix: ...`).
   * Отправка в удаленный репозиторий GitHub для бесшовной синхронизации между ПК и MacBook.
4. **Фиксация в Walkthrough (`walkthrough.md`) и обновление якоря памяти (`PROJECT_STATE.md`)**:
   * Краткий отчет о проделанной работе, пройденных тестах и инструкции по запуску.
   * Обновление файла `PROJECT_STATE.md` (или `GEMINI.md`) в корне проекта (см. раздел 3).

---

## 3. Защита контекста на длинной дистанции: Сабагенты и Вечная Память

Чтобы агент **никогда не терял контекст** при разработке крупных проектов (игр, сервисов из 20+ файлов) или при переходе между чатами:

1. **Делегирование Сабагентам (`invoke_subagent`) — Изоляция чернового контекста:**
   * Если нужно просканировать >5–10 файлов, изучить чужой SDK или провести глубокий поиск по документации — главный агент вызывает сабагента (`research` или `self` через `invoke_subagent`).
   * В **Фазе 3 (Adversarial TDD)** и **Фазе 5 (Аудит)** при сложных задачах главный агент может поручить сабагенту роль независимого QA-аудитора («найди, как сломать этот код»).
   * Сабагент выполняет всю черновую работу в своем изолированном окне и возвращает главному агенту только **сжатое саммари (200–300 токенов)**. Основной диалог остается кристально чистым.

2. **Живой якорь памяти проекта (`PROJECT_STATE.md` / `GEMINI.md` в корне репозитория):**
   * В каждом проекте, который ведется в «Режиме ПРО», агент создает и поддерживает в корне рабочей папки компактный файл `PROJECT_STATE.md` (строго до 60–80 строк):
     * **Архитектура и стек** (например: *Unity 6 WebGL / Яндекс Игры SDK (YG2), EventBus*).
     * **Реализованные модули и их контракты** (список готовых скриптов/пакетов с 1 строкой описания).
     * **Жесткие инварианты и ограничения** (что нельзя ломать).
     * **Текущий этап и следующий шаг (Next Up)**.
   * Это дает 100% иммунитет к переполнению контекста: в любой момент (или в совершенно новом чате) агент читает `PROJECT_STATE.md` и за 500 токенов мгновенно вспоминает всё устройство проекта.
