## Блок 1: Рантайм и Модель памяти

### 1. Как устроен планировщик Go (Модель GMP)?
* **G (Goroutine)**: структура, описывающая горутину (стек, указатель команд PC, флаги состояния). Начальный размер стека всего ~2-4 КБ, растет динамически при необходимости.
* **M (Machine / OS Thread)**: поток операционной системы, выделенный ОС. Выполняет код горутины.
* **P (Processor)**: логический контекст планирования, ресурс, необходимый для выполнения кода Go. Количество `P` по умолчанию равно `GOMAXPROCS` (числу логических ядер CPU).
* **Work Stealing**: у каждого `P` есть локальная очередь задач (на 256 горутин) и общая глобальная очередь. Если локальная очередь пуста, `P` пытается украсть половину задач у другого `P`, а затем проверяет глобальную очередь и netpoller.
* **Syscall / Блокировка**: если `M` блокируется в системном вызове, `P` отсоединяется от `M` (handoff) и связывается с другим свободным или новым потоком `M`, чтобы остальные горутины продолжали работать.

### 2. Как работает Garbage Collector (GC) в Go?
* Используется **конкурентный трехцветный алгоритм маркировки (Tri-color Mark and Sweep)** с барьером записи (Write Barrier).
* **Цвета**:
  * **Белые**: не посещенные объекты (потенциальный мусор).
  * **Серые**: посещенные объекты, чьи дочерние ссылки еще не исследованы.
  * **Черные**: посещенные объекты, все дочерние ссылки которых проверены (гарантированно живые).
* **Фазы**:
  1. *Sweep Termination* (STW — доли миллисекунды): включение барьера записи.
  2. *Marking* (Конкурентная): GC-воркеры работают параллельно с горутинами приложения, крася объекты.
  3. *Mark Termination* (STW — доли миллисекунды): завершение маркировки, выключение барьера записи.
  4. *Sweeping* (Конкурентная): возврат неокрашенной памяти в аллокатор.
* Регулируется параметром `GOGC` (по умолчанию 100% — сборка запускается, когда размер кучи удваивается) и `GOMEMLIMIT` (лимит памяти с Go 1.19).

### 3. Стек против Кучи: Escape Analysis (анализ побега)
* Компилятор Go решает, где выделить память переменной:
  * На **стеке**: быстро (просто смещение указателя стека), очищается мгновенно при выходе из функции, не нагружает GC.
  * В **куче**: если переменная может пережить контекст функции (указатель возвращается наружу, передается в `interface{}`, размер неизвестен на этапе компиляции или слишком велик).
* Команда проверки: `go build -gcflags="-m"`.

## Блок 2: Внутреннее устройство структур данных

### 4. Как устроен слайс (`slice`)?
* Это заголовок из 3 полей (24 байта на 64-битной системе):
  ```go
  type slice struct {
      array unsafe.Pointer // указатель на базовый массив
      len   int            // текущая длина
      cap   int            // вместимость базового массива
  }
  ```
* При передаче слайса в функцию копируется этот заголовок (значение указателя то же, но изменения `len` наружу не видны без возврата или передачи по указателю).
* `append`: если `len < cap`, элемент пишется в свободную ячейку. Если `len == cap`, выделяется новый массив большего размера (до 256 элементов растет в 2 раза, затем плавно ~1.25), старые данные копируются.

### 5. Как устроена `map`?
* Хэш-таблица на основе бакетов (`bmap`). Каждый бакет вмещает до 8 пар ключ-значение.
* Заголовок `hmap`: счетчик `count`, количество бакетов `B` (всего $2^B$ бакетов), указатель на массив бакетов `buckets`.
* Поиск: хэш-функция вычисляет хэш ключа. Младшие биты определяют номер бакета, старшие 8 бит (`tophash`) используются для быстрого сравнения внутри бакета.
* Коллизии: если в бакете закончились места, создается overflow-бакет (связный список).
* Рост: если `load factor > 6.5` или слишком много overflow-бакетов, выделяется массив бакетов в 2 раза больше, и происходит инкрементальная эвакуация данных при последующих записях/удалениях.
* **Потокобезопасность**: мапа не защищена от одновременной записи. При одновременном чтении и записи рантайм вызовет фатальную панику `fatal error: concurrent map writes`. Для параллельного доступа нужен `sync.RWMutex` или `sync.Map`.

### 6. Внутренности интерфейсов: `iface` vs `eface`
* **`eface` (пустой интерфейс `interface{}` / `any`)**:
  ```go
  type eface struct {
      _type *_type         // динамический тип значения
      data  unsafe.Pointer // указатель на данные
  }
  ```
* **`iface` (непустой интерфейс с методами)**:
  ```go
  type iface struct {
      tab  *itab          // таблица методов и информация о типе
      data unsafe.Pointer // указатель на данные
  }
  ```
* **Подводный камень**: Интерфейс равен `nil` только тогда, когда **и тип, и данные равны `nil`**. Если присвоить интерфейсу типизированный `nil`-указатель (например `var err *MyCustomError = nil; var i error = err`), то `i != nil`, так как тип `_type` заполнен!

## Блок 3: Каналы и Конкурентность

### 7. Как устроен канал внутри (`hchan`)?
* Это структура с кольцевым буфером, защищенная внутренним мьютексом:
  ```go
  type hchan struct {
      qcount   uint           // количество элементов в буфере
      dataqsiz uint           // емкость буфера (make(chan T, size))
      buf      unsafe.Pointer // указатель на кольцевой буфер
      elemsize uint16
      closed   uint32
      elemtype *_type
      sendx    uint           // индекс для отправки
      recvx    uint           // индекс для чтения
      recvq    waitq          // очередь заблокированных читателей (горутин)
      sendq    waitq          // очередь заблокированных писателей (горутин)
      lock     mutex          // внутренний спинлок/мьютекс
  }
  ```
* Небуферизованный канал имеет `dataqsiz = 0`. При передаче данных писатель напрямую копирует значение в память горутины-читателя (минуя буфер), если читатель уже ждет в `recvq`.

### 8. Состояния канала и операции:
| Операция | `nil` канал | Открытый (с данными / пустой) | Закрытый канал |
| :--- | :--- | :--- | :--- |
| **Чтение (`<-ch`)** | Вечная блокировка | Читает значение или блокируется | Читает оставшиеся значения, затем zero value (`v, ok := <-ch`, `ok == false`) |
| **Запись (`ch <- v`)** | Вечная блокировка | Записывает или блокируется | **Паника (`panic: send on closed channel`)** |
| **Закрытие (`close(ch)`)** | **Паника** | Закрывает канал | **Паника (`panic: close of closed channel`)** |

### 9. В чем разница между `sync.Mutex` и `sync.RWMutex`?
* `sync.Mutex` — эксклюзивная взаимная блокировка. Только одна горутина может захватить замок.
* `sync.RWMutex` — разделяемая блокировка для чтения (`RLock`/`RUnlock`) и эксклюзивная для записи (`Lock`/`Unlock`).
* `RWMutex` эффективен только тогда, когда чтений значительно больше, чем записей (90%+ чтений), иначе накладные расходы на учет количества читателей делают его медленнее обычного `Mutex`.

## Блок 4: Архитектура и Продакшен

### 10. Как правильно делать Graceful Shutdown сервера?
```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

srv := &http.Server{Addr: ":8080", Handler: router}

go func() {
    if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
        log.Fatalf("listen error: %v", err)
    }
}()

<-ctx.Done() // Ожидание сигнала SIGINT / SIGTERM

shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

if err := srv.Shutdown(shutdownCtx); err != nil {
    log.Fatalf("forced shutdown: %v", err)
}
```

### 11. Зачем нужен `context.Context` и каковы 4 золотых правила?
1. Первым аргументом в функции с именем `ctx`.
2. Никогда не передавать `nil`, использовать `context.Background()` или `context.TODO()`.
3. Никогда не сохранять в полях структур.
4. Значения через `WithValue` использовать только для данных сквозного контекста запроса (RequestID, TraceID, Auth Claims), а не для передачи параметров бизнес-логики.
